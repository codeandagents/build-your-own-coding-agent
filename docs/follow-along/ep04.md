# Episode 4: the sandbox

Follow-along for **Build Your Own Claude Code**, episode 4 ([video](https://www.youtube.com/@CodeAndAgents)). Same
setup as [episode 1](ep01.md), plus [Docker](https://docs.docker.com/get-started/get-docker/) (Docker Desktop on Windows
and macOS), running. This episode's harness is the tag `ep04`; last episode's is `ep03`.

| Tag | Where the agent's shell commands run | Tries | Score |
|---|---|---|---|
| `ep03` | on your computer, behind a list of refused command patterns (`curl`, `find /`, `.env`...) | 45 | 36 |
| `ep04` | in a Docker container per task: no network, one folder shared with your computer (the project); without Docker, every command waits for your yes | 45 | 35 |

Your runs will differ in the details: the model doesn't answer the same way twice.

```bash
git checkout ep04
uv sync
docker build -t byoca-sandbox sandbox     # once: the sandbox's image (about a minute)
uv run pytest -q                          # offline, no key; the Docker tests skip if Docker isn't running
```

## Step 1: how it got out

In episode 2's runs (tag `ep02`), one try of task t10 started with `cd ~-`: "go back to the folder you came from".
Bash keeps that folder in `OLDPWD`, and every command inherited the harness's own: the folder the benchmark had been
started from (mine holds my notes for this series). A grep there printed 20 lines of those notes, including the table
that describes t10's hidden check, and the try passed. That pass doesn't count (episode 2's file-tools step: 60 of 90,
not 61).

The rails of episodes 1-3 were a list of patterns, kept in `bench/escape.py` as `OLD_RAILS` to compare. None of them
matches `cd ~-`. And `grep -rIl -i "public holiday\|closure" / ...` (a whole-disk search from an episode 2 run) got past
the search pattern `\b(grep|rg)\b[^|;&]*\s/`: `[^|;&]*` stops at the first `|`, the one inside `\|`, so the pattern
never reaches the `/`. The command ran until the 60-second timeout killed it.

Until episode 4, start runs from a folder with nothing private in it, or `unset OLDPWD` first.

## Step 2: Claude Code's way

From Claude Code's docs ([permissions](https://code.claude.com/docs/en/permissions),
[sandboxing](https://code.claude.com/docs/en/sandboxing),
[sandbox environments](https://code.claude.com/docs/en/sandbox-environments)):
- **Permissions:** rules are checked before a tool runs, deny, then ask, then allow. A Bash rule matches the command's
  text, so it "isn't a security boundary around the program": `Bash(curl *)` doesn't stop `/usr/bin/curl ...` or
  `sh -c 'curl ...'`.
- **The sandbox:** a boundary the operating system enforces around shell commands only (writes to the working
  directory and a temp folder; network through a proxy whose allowed domains start empty). Reads stay open by default:
  "most of the machine". The file tools follow the permission rules instead.
- **Native Windows:** Claude Code runs commands unsandboxed; for a Windows host the docs suggest "a container or VM, or
  run the Bash sandbox inside WSL2". This series runs on Windows, so the sandbox is a container.

## Step 3: build the box

Open `agent/sandbox.py`:
- `Sandbox(folder)`: one container per task (`docker run ... sleep infinity`) with `--network none`, `--read-only` plus
  its own `/tmp`, the project mounted at its own path (Git Bash style on Windows, so a path from `pwd` works in the file
  tools), `HOME` = the project, `--cap-drop ALL`, `no-new-privileges`, 512 processes, 2 GB;
- `run()`: `docker exec NAME timeout --kill-after=5 60 bash -c COMMAND`. `docker exec` passes none of your
  environment; `timeout` stops the command and everything it started.

And `agent/tools.py`:
- `bash()`: in the sandbox every command runs; without one, `approve()` asks `Run it outside the sandbox? [y/N]`, and
  nobody at the keyboard (stdin isn't a terminal) means no;
- `bench.run` refuses to start without the sandbox; `python -m agent` falls back to asking;
- the bash tool's description says where commands run (`WHERE`);
- the file and search tools run on your computer, behind the path check: inside the project, no `.env`.

```bash
uv run pytest -q tests/test_sandbox.py      # 16 tests; the Docker ones skip if Docker isn't running
```

What to look for: `16 passed`. If you see `skipped`, Docker isn't running or the image isn't built.

## Step 4: try to break out

`bench/escape.py` runs ten commands that reach past the folder (six of them from this series' own logs; then Claude
Code's own network check, the next step after `ls ..`, and two for secrets) and four harmless ones, in the sandbox. Beside the project it puts
another task's folder and a `.env` file, each with a random marker, a marked database URL in the harness's
environment, and `OLDPWD` pointing at the other task. A command "got out" if a marker shows in its output, a file
outside the project appears or changes, or a network command succeeds. The rails' column only matches the command's
text: they are never run on your computer.

```bash
uv run python -m bench.escape            # free, no key, about 20 seconds
```

What to look for: the last two lines, `Episodes 1-3's rails refused 4 of 10 attempts to get out, and 1 of 4 harmless
commands.` and `The sandbox contained 10 of 10, and ran 4 of 4 harmless commands.`, and in the table each attempt's
reason (`Read-only file system`, `Could not resolve host`, `No such file or directory`). If it stops with "the sandbox
can't start", start Docker or build the image.

## Step 5: the score, and a look around

```bash
uv run python -m bench.board results/ep03.jsonl | tail -1
uv run python -m bench.board results/ep04.jsonl
uv run python -m bench.run --tasks t15 --brief      # live, in the sandbox: a cent or two
```

36 of 45 at `ep03`, 35 of 45 at `ep04`: the same score within the run-to-run spread (about ±3), as expected of a
safety feature. No try failed because of the container; the failures are the usual ones (t04's `clinic_today`, t12's
rules and t15's list outside the project, one t08 try that merged 3 of 5 duplicates).

What changed is where the agent's hunts end. In the 45 tries, seven commands the old rails would have refused ran, and
each met an empty container: `find /` for task files found only the task's own folder, and listing the folder above
the project (on your computer it holds every task's copy) showed one folder. In the video's t15 run: `find / -iname
"*closure*"`, then `ls /c/.../byoca-work/`, whose first line is the task's own folder, the only one; it ended saying the
list is "not reachable from my sandbox". In the video, the first six turns were read back from my recording of the benchmark's first try (`.runs/cassettes`, not in the repo);
yours are live from the start, and may go another way.

What the sandbox doesn't cover: the project folder itself (the agent can still break it, or follow an instruction
planted in one of its files: t14 has one), what the agent reads (it still goes to the model's API), and the kernel (a
container shares it with the machine Docker runs on: on Windows and macOS, Docker Desktop's Linux VM; a virtual machine
of its own is a stronger wall). Claude Code's docs say the same: "any approach that mounts your project directory writable can still modify that code", and "Isolation
also does not change what is sent to the model".
