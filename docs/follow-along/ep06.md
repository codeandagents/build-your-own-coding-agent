## Step 1: why task twelve fails

`bench/tasks/t12-senior-discount/task.md` asks for a "Senior pet discount": 10% off the consultations for a pet aged 10
or older on the day of its visit. The only discount in the code is PetCover's (`petclinic/billing/insurance.py`): the
whole invoice, rounded down, at the end. The clinic's own rules (their own line, right after the last consultation,
the percentage in the name, half up) are in no file of the project. Before this episode, task 12 failed all 39 of its
tries.

```bash

```

## Step 2: Claude Code's two kinds of memory

From [How Claude remembers your project](https://code.claude.com/docs/en/memory):
- "Each Claude Code session begins with a fresh context window. Two mechanisms carry knowledge across sessions":
  **CLAUDE.md files**, "instructions you write", and **auto memory**, "notes Claude writes itself based on your
  corrections and preferences".
- "Both are loaded at the start of every conversation. Claude treats them as context, not enforced configuration."
- With no `CLAUDE.md`, Claude Code reads `AGENTS.md` instead (from v2.1.277). A subfolder's `AGENTS.md` loads "when
  Claude opens a file there with the Read tool"; a subfolder's `CLAUDE.md` once Claude "reads, writes, or edits another
  file in that subdirectory".
- Auto memory lives in `~/.claude/projects/<project>/memory/`: "a MEMORY.md index and one topic file per memory". "The
  first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every
  conversation"; topic files are read "on demand".
- What it saves: four kinds (user, feedback, project, reference). "Claude skips anything it can derive from the
  codebase ... It also skips anything your CLAUDE.md files already say." "When you ask Claude to remember something ...
  Claude saves it to auto memory."

## Step 3: load it at the start

Open `agent/memory.py`. `first_message()` puts a `<context>` block before the task: the project's instruction files
(`folder_files()`: its CLAUDE.md files, or else its AGENTS.md), then the memory's index (`index()`: 200 lines or 25KB).
`nested()` adds a subfolder's instructions to the first `read_file` result there (our project has
`petclinic/billing/AGENTS.md`). `PROMPT` is the system prompt's memory section: where the folder is, when to save a
note, what to skip, one file per note and one line in `MEMORY.md`. In `agent/tools.py`, `also()` lets the file tools use
the memory folder (and nothing else outside the project) while a session runs; in `agent/sandbox.py`, the folder is
mounted into the container read-only.

```bash
uv run pytest -q tests/test_memory.py     # 17 passed, offline
```

## Step 4: yesterday

`bench/yesterday.py` runs `bench/sessions/multi-pet/task.md` with an empty memory. When the agent stops, it sends code
review's reply, `review.md`, and the line in `remember.md` (`--no-remember` leaves it out). The hidden check scores the
fix, and the memory folder is kept in `.runs/memory/<label>/r<N>/`.

```bash
uv run python -m bench.yesterday --brief          # live, about a cent: .runs/memory/yesterday/r0
cat .runs/memory/yesterday/r0/MEMORY.md .runs/memory/yesterday/r0/*.md
```

Look for the reply in bold, then the note: two `write_file` calls into the memory folder. In our capture it first tried
`cat > ... <<'EOF'` in the shell and got `Read-only file system`, then used the file tools. Our three sessions'
notes are in `results/ep06-memory/yesterday/`; two of them, and our capture's, end by naming a helper that only that
session's code had.

## Step 5: today

```bash
uv run python -m bench.run --tasks t12 --memory .runs/memory/yesterday --brief    # live, about a cent
```

Each try starts from a fresh copy of the project and a fresh copy of the memory folder (`--memory FOLDER`; a folder with
`r0`, `r1`... gives try N its own). Look for `[memory: ... 1 line]`, the note in the first command, and the discount
line right after the consultations. In our capture, its summary ended: "my saved note on clinic discount rules says to
use `billing/invoices.consult_discount()`, but no such function exists."

The first full run had no read-only share: the shell couldn't see the memory folder (`git checkout ep06-blind`).
Task 12, try 2, reached for its note with `cat`, `ls` and `find /`, found nothing, and failed. Claude Code's sandboxed
shell ([sandboxing](https://code.claude.com/docs/en/sandboxing)) reads "Most of the machine" and writes only the
working directory and a temp folder; `~/.claude` is protected. Ours now shares the memory folder, read-only.

```bash
for r in ep04 ep06-blind ep06; do uv run python -m bench.board results/$r.jsonl | grep t12; done
```

## Step 6: the score

```bash
ls results/ep06-memory/control                                   # r1: one of three sessions saved a note
uv run python -m bench.board results/ep06-control-t12.jsonl      # FAIL PASS FAIL
for r in ep04 ep06; do uv run python -m bench.board results/$r.jsonl | tail -1; done   # 35/45 both
```

Unasked, one session in three saved its note ("since they're a standing rule that isn't in the repo"), and task 12
passed only on that one. On the whole benchmark the total held at 35: task 12 gained three tries, the others lost about
as many, some by the usual noise. One habit changed in every try: with instructions and notes in the first message, the
agent reads through the shell (`read_file` calls: 23 in episode 4, 0 on the `ep06` board; first calls in the shell: 31,
then 45 of 45). A shell output over 30,000 characters is saved with a 2,000-character preview (episode 3), and task 6
try 3 read only the ticket's start and end. We changed three things at once (the instructions, the memory, bash's
description), so the cause isn't known.
